# YOLO OBB 样例图地理检测 Demo 设计文档

## 背景
当前项目目录仅包含一个 OBB 检测权重文件 `yolo26n_obb_fair1m.pt` 与一个样例数据目录 `sample_100_mix/`。样例目录中包含：

- 100 张测试图片
- `manifest.txt`：样例图与来源路径映射
- `geo.json`：图片地理元数据、仿射参数、图片中心点、边界范围，以及原始标注对象的像素点与地理点

目标是在此基础上快速实现一个可运行的网页 demo，用已有权重模型对样例图进行检测，并同时展示检测图与对应地理信息。

## 目标
构建一个仅面向 `sample_100_mix/` 样例图的轻量 Gradio 网页 demo，满足以下要求：

1. 用户可从样例图列表中选择一张图片。
2. 系统使用 `yolo26n_obb_fair1m.pt` 对该图片执行一次 OBB 检测。
3. 页面展示带检测框的结果图。
4. 页面优先展示图片中心点经纬度。
5. 页面最多展示 5 个检测框结果，每个结果默认折叠。
6. 每个检测项展示类别、置信度、检测框中心点像素坐标、检测框中心点经纬度。

## 非目标
首版 demo 不包含以下能力：

- 用户上传本地图片
- 对非 `geo.json` 管理的图片计算经纬度
- 批量检测
- 历史结果保存
- 独立后端服务/API
- 数据库或任务队列
- 复杂前端视觉定制

## 方案对比

### 方案 A：Gradio + Ultralytics 推理 + geo.json 映射
使用 Gradio 构建单页应用，用户从样例图下拉框中选择图片，点击按钮执行推理。模型输出检测结果图，地理信息由 `geo.json` 中对应图片的 `affine` 与 `center` 数据提供。

优点：实现最快、依赖少、适合当前 demo 目标。  
缺点：页面可定制性一般，后续如果演进为正式服务可能需要重构。

### 方案 B：Gradio + 启动时元数据缓存
在方案 A 基础上，启动时预加载 `geo.json` 和图片列表缓存，减少交互时的重复解析。

优点：交互更顺畅，结构上更适合扩展。  
缺点：相比当前需求多一层抽象，首版略重。

### 方案 C：API 层 + Gradio 前端
将推理与地理换算做成后端 API，Gradio 仅负责展示。

优点：后续扩展为服务更平滑。  
缺点：超过当前“简单 demo”的实现边界。

## 最终选择
选择**方案 A**作为首版落地方案。

理由：当前已有权重、图片与地理元数据，需求重点是尽快得到一个可演示的网页。Gradio 能以最小实现成本完成交互闭环，不需要过早引入 API 边界或额外架构。

## 整体架构
项目拆为 4 个职责清晰的模块：

1. `app.py`  
   Gradio 应用入口，负责界面布局、事件绑定、状态提示和结果展示。

2. `inference.py`  
   负责模型加载、单张图片 OBB 推理、结果图生成，以及从模型输出中提取检测结果。

3. `geo_mapper.py`  
   负责读取 `sample_100_mix/geo.json`，根据图片名获取图片地理元数据，并将检测框中心点从像素坐标转换为经纬度。

4. `data_loader.py`  
   负责列出样例图、整理图片选项、读取与查询基础元数据。

这种拆分方式能让界面、模型推理、地理换算各自独立，便于快速实现，也便于后续局部替换。

## 页面交互设计
页面为单页应用，采用从上到下的线性信息结构：

1. **图片选择区**  
   - 下拉框：列出 `sample_100_mix/` 中可选图片文件名
   - 按钮：`开始检测`

2. **图片基础地理信息区**  
   检测完成后优先展示：
   - 图片文件名
   - 图片中心点经纬度
   - 图片尺寸
   - 可选展示边界范围 `bounds`

3. **检测结果图区**  
   展示带 OBB 检测框的结果图。

4. **检测框结果区**  
   - 最多展示前 5 个检测结果
   - 每个结果为默认折叠的面板
   - 展开后展示：类别名、置信度、中心点像素坐标、中心点经纬度

5. **状态提示区**  
   用于展示“模型加载中”“首次推理较慢”“检测完成”“无检测结果”“地理信息缺失”等状态。

该结构优先保证：先看到图片整体位置，再看检测图，最后按需展开目标明细。

## 数据流与计算流程

### 输入
用户仅能从 `sample_100_mix/` 中选择图片，不支持上传外部图片。

### 推理流程
1. 用户选择图片并点击检测按钮。
2. 应用获取图片绝对路径。
3. `inference.py` 懒加载 `yolo26n_obb_fair1m.pt`。
4. 模型对该图片执行一次 OBB 推理。
5. 从模型结果中提取每个检测目标的类别、置信度与几何信息。
6. 生成并返回绘制后的检测图。

### 中心点计算流程
对于每个检测框，优先使用模型 OBB 输出的顶点或旋转框信息求中心点；若实际接口不便直接获取顶点，则退化为使用外接框中心点作为近似中心。

中心点计算结果至少包括：
- `pixel_center_x`
- `pixel_center_y`

### 经纬度映射流程
1. 根据图片名在 `geo.json` 中定位对应记录。
2. 直接读取图片中心点 `center` 作为图片中心点经纬度展示值。
3. 读取该图片的 `affine` 参数。
4. 将检测框中心点像素坐标映射为经纬度。
5. 整理出页面展示所需结构。

## 数据模型建议

### 图片元数据
每张图片至少整理为以下字段：

- `image_key`
- `image_name`
- `image_path`
- `width`
- `height`
- `center_lon`
- `center_lat`
- `bounds`
- `affine`

### 单个检测项
每个检测结果至少整理为以下字段：

- `index`
- `class_name`
- `class_id`
- `confidence`
- `pixel_center`
- `geo_center`

## 错误处理
仅处理与首版 demo 强相关的问题：

1. **权重文件不存在**  
   页面提示模型文件缺失，停止推理。

2. **`geo.json` 缺失或图片键不存在**  
   页面提示无法获取地理信息，检测结果图仍可返回；若地理映射无法完成，则检测框地理信息区域给出明确说明。

3. **无检测结果**  
   返回原图或绘制后的空结果图，并提示“未检测到目标”。

4. **首次推理耗时较长**  
   页面状态区提示首次加载模型可能较慢。

不额外加入复杂重试机制、后台任务或缓存失效处理。

## 测试与验证范围

至少覆盖以下行为：

- 能成功加载 `geo.json`
- 能正确生成样例图列表
- 给定像素点后，能通过 `affine` 计算经纬度
- 能将检测结果整理为前端可展示格式

### 手工运行验证
至少验证以下链路：

- 页面可以启动
- 可选择样例图
- 可成功执行一次检测
- 可展示图片中心点经纬度
- 可展示检测结果图
- 可展示最多 5 个折叠检测项

## 成功标准
当以下条件满足时，视为首版 demo 达成目标：

1. 在本地运行后可打开网页界面。
2. 页面可从 `sample_100_mix/` 中选择图片。
3. 点击后可完成模型检测并显示结果图。
4. 页面顶部明确展示图片中心点经纬度。
5. 页面最多展示 5 个折叠检测项。
6. 每个检测项可显示类别、置信度、中心点像素坐标、中心点经纬度。
7. 常见缺失场景能得到清晰提示，而不是直接崩溃。
